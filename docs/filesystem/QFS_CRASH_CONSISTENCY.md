# QFS v2 崩溃一致性与恢复协议

## 磁盘布局与兼容性

QFS v1 保持原布局：超级块为扇区 0，位图为 1–8，inode 表为 9–16，目录为
17–24，数据区从 25 开始。v1 卷仍可挂载和读取，但会以只读方式挂载。不会自动
原地迁移，因为 v1 的 25 号扇区之后可能存放用户数据，而 v2 会将这一区域用作日志。

QFS v2 保留原有元数据位置，并将 25–37 号扇区固定为 redo journal：25 为日志头，
26–35 最多存放十个完整扇区的 after-image，36 和 37 为两份独立校验的提交记录。
数据区从 38 开始。分区最小仍为 64 个扇区。文件系统仍然只有一个平面根目录，
单文件上限仍为 4 KiB；本阶段不宣称增加目录层级或 extent 支持。

## 事务提交顺序

1. 在内存中暂存所有变更后的 home sector。单次事务最多十个不同扇区：最多八个
   文件数据扇区、一个位图扇区和一个 inode 扇区；创建、删除事务也不超过此上限。
2. 写入日志 payload 和带 CRC32 的日志头，然后执行设备 flush。
3. 写入两份提交记录，然后执行设备 flush。任一有效提交记录都足以触发恢复。
4. 将完整 after-image 幂等重放到原始扇区，然后执行设备 flush。
5. 清除两份提交记录，然后再次执行设备 flush。

挂载时先检查提交记录、日志头、目标 LBA 和每个 payload 的 CRC，再重放日志，最后
才加载并校验位图、inode 和目录。没有有效提交记录的未提交日志不会写入 home sector；
非零但校验失败的提交区会导致挂载失败关闭，不会静默接受不确定状态。

## 持久化屏障

QFS v2 要求块设备提供真实的 flush 回调。未提供回调时，`qm_block_flush()` 返回
`QM_ERR_NOT_SUPPORTED`，不会再假装刷新成功。IDE PIO 驱动使用 ATA FLUSH CACHE
（`0xE7`）并向上传递错误。

一致性保证依赖设备遵守 flush 完成语义，并正确处理已完成的 512 字节扇区写入。
CRC32 用于检测日志撕裂或损坏，不是加密认证；任何软件协议都无法补偿设备谎报 flush
完成或硬件本身损坏数据的情况。

## 格式化行为

格式化先清除旧超级块并 flush，使旧卷在元数据被覆盖前变为不可挂载；随后清空日志、
初始化位图/inode/目录并 flush；最后写入带 CRC 的 v2 超级块并 flush。格式化过程中断
可能留下不可挂载卷，但不会把混合的新旧元数据当成有效文件系统。格式化是破坏性操作；
v1 数据应先备份或导出。当前不进行自动原地迁移。

## 故障注入验证

执行 `bash tools/qfs/run_crash_tests.sh` 会编译并运行现有 QFS 主机测试，以及单独的
易失缓存/持久介质双镜像故障注入测试。测试会对 create、多扇区 write、remove、format
的每一个观测到的写入/flush 回调边界注入错误，恢复到最后一次持久镜像并模拟断电。
此外还会在 journal replay 的每个写入/flush 边界再次中断恢复，验证多次重启后的幂等性。
测试同时确认 v1 文件仍可读取、v1 修改请求被拒绝，以及缺少 flush 回调的设备不能格式化
QFS v2。
